## 0. What LYNX does now

| Format | Opens as | Status |
|---|---|---|
| `.dwp` FL DirectWave program | a DirectWave channel (the program as saved, samples found as DirectWave finds them) | full: every field DirectWave's engine plays |
| `.dwb` FL DirectWave bank | a DirectWave channel with the bank's state (the first program with zones; after round 190hz: MIDI slot 0's program) | full |
| `.gig` GigaStudio / LinuxSampler | a DirectWave channel per chosen instrument; samples written out as WAV | zones, velocity splits, layers, round robin / random, envelope, loops, tuning, pan, attenuation, key groups; the rest reported |
| `.ncw` Kontakt's compressed WAV | an audio file everywhere a sample is accepted (Browser, rack, playlist, zones) | full decode (delta / raw, mid/side, 8/16/24/32-bit, floats) |
| `.nki` Kontakt instrument | recognised; the import dialog says what it is and that it is not imported | detection only (see §3) |

The hook: every format ends as a DirectWave state handed to **`dw::importChannel`** (`src/core/DirectWave.h`, unchanged —
the same entry an `.flp`'s DirectWave channel takes). `src/core/DirectWave.{h,cpp}` and the editor files of round 190hz
are not touched. New files: `src/core/SamplerImport.{h,cpp}` (neutral program → state, .dwp / .dwb, sample search,
WAV writer), `src/core/GigFile.{h,cpp}`, `src/core/Ncw.{h,cpp}`, `src/core/KontaktFile.{h,cpp}`,
`src/engine/NcwFormat.{h,cpp}` (JUCE reader), `src/ui/SamplerImportUi.{h,cpp}` (Browser / rack glue, the report dialog).

## 1. DirectWave program and bank files

### 1.1 Layout [DEC + DATA]

- `.dwp` = `"DwPr"` + u32 version + the state's chunks (u32 id, u64 size, body) — the writer `0x180014140` puts the
  version, the flags chunk (6, 16 bytes) and one program record (chunk 1). `.dwb` = `"DwBk"` + the whole state
  (`0x180014020`). After the magic both are exactly a channel state (REA_rodada9 §2): LYNX strips the 4 bytes.
- Versions: the shipped files are **36** (26 files) and **37** (6); FL 2026 writes 38. LYNX accepts 36…38 like
  `dw::parseState`.
- "Save for FL Studio Mobile" (`0x180020950`) first copies the zones' samples into the content library's
  `Imported/` folder, rewrites the zone paths, then saves the program through the same writer.

### 1.2 Short records [DEC `0x18003f840`, `0x180003e80`]

DirectWave reads each chunk with `read(min(chunk size, record size))` into a record that starts zeroed (the sample
format record starts with bit depth 32), so a short chunk keeps the defaults for its missing tail. **The shipped
version-36 files store the sample format record (0x1F7) with 36 bytes** (no bit depth): 1,048 of their 1,101 zones.
LYNX's `readZone` requires 40 bytes and skipped the whole record — with it the loop mode and loop points: those
programs played without their loops. LYNX now completes short records the way DirectWave reads them before
`dw::parseState` sees the state (`msimport::stateOfFile`). *Suggestion for the rollup*: the same tolerance in
`readZone` (accept 36 bytes, bits = 32) would also fix version-36 states inside old `.flp` projects; it is left to
the round that owns DirectWave.cpp (190hz touches the neighbouring lines).

*Rollup 0.1.30 (round 190il):* the tolerance moved into `readZone` itself (DirectWave.cpp: every zone record shorter than
LYNX reads is completed with zeros, the sample format record's bit depth with 32), so version-36 states in old `.flp`
projects and the DirectWave editor's "Open program" keep their loops too; `msimport::stateOfFile` now keeps the file's
records as stored and relies on it (tests/Rollup030Tests.inc).

### 1.3 Finding the samples [DEC `0x18001ddb0` → `0x18001dc20`, `0x180006590`, `0x180040350`]

When the zone's saved path does not open, DirectWave (with "find missing samples" on):
1. builds `<program file without its extension>/<the sample's file name>` (`0x1800054a0` strips the extension,
   `0x1800062d0` takes the file name after the last `\` or `/`) — the layout of FL's packs: `Piano 2.dwp` next to a
   folder `Piano 2` holding the samples;
2. asks the host (FL, dispatcher opcode 0x0E: FL's own sample search over its folders);
3. searches the DirectWave content library folder recursively for the file name (`0x180006590`,
   `FindFirstFileW` over `*.*`; the folder comes from Image-Line's shared path manager, `0x180022f60`).

Path variables (`%FLStudioData%`, `%ILSharedData%`, `%USERPROFILE%` in the shipped files) are FL's: the plugin
contracts paths on save (`0x18003efe0`) and the host expands them. `0x180040350` repairs a doubled
`%FLStudioFactoryData%\…%Var%…` prefix by keeping the part from the last `%…%` variable.

LYNX's order (`msimport::findZoneSample`): the saved path with FL's variables (`resolveFlPath`; `%USERPROFILE%` = this
user's profile), the saved path as it is, step 1, then — standing in for FL's host search — the program file's own
folder and a bounded search below it (20,000 entries), then step 3 in `%ILSharedData%\DirectWave` (where FL's
shipped FL Studio Mobile programs point).

Shipped files [DATA]: the paths point at `%FLStudioData%\Patches\Packs\<pack>\…` (1,048 zones), but FL 2026 moved
the packs to `Packs\Legacy\…`; step 1 finds them for the instruments (`Piano 2.dwp` + `Piano 2\`), the drum kits keep
their samples next to the program (`Drum Kit 08\World Drum.dwp` + `Drum Kit 08\*.wav`), found by LYNX's step 3.
A third layout needed one more LYNX step: the guitar, bass and orchestral programs keep the saved path's own last
folder next to the program (`Guitar\Bass\FLStudio Bass Pluck.dwp` + `Guitar\Bass\FLStudio Bass 02\…`, the nine
`Acoustic Guitar 0N.dwp` all on `Acoustic Guitar 01\`), so LYNX also tries `<program folder>/<saved folder name>/
<file>`. FL's names were written for a case-insensitive disk (`…B0OGG.WAV` is `…B0ogg.wav`): on POSIX systems the
spelling on disk is looked up.

**Result on FL 2026's 32 shipped programs** (env-gated test `formats190ii_fl_shipped_programs`): all 32 import, 1,101
zones, **every sample found**; the forward loops of the version-36 programs (lost before, §1.2) are kept.

### 1.4 What plays

The whole program record is the channel's state, so everything DirectWave's engine reproduces (REA_rodada72) plays:
zones, key / velocity ranges, root, tuning, gain, pan, loops (5 modes), sample offset, both filters, amplitude and
modulation envelopes, LFOs, the modulation matrix, the zone effects, sends, alternation and exclusive groups, the
program's effects. Embedded audio (0x205) is written out as WAV like an `.flp`'s.

## 2. GigaStudio `.gig`

### 2.1 Licence and the reader

libgig (C. Schoenebeck) is **GPL-2.0-or-later** — every source header of libgig 4.4.1 says "either version 2 of the
License, or (at your option) any later version" — so it could be combined with LYNX's AGPL-3.0 through the GPLv3.
It was **not** compiled in: its CMake file only generates MSVC solutions (`FATAL_ERROR` otherwise), MinGW builds need
its configure-generated `config.h` / `libgig_private.h`, it is ~20,000 lines (RIFF, DLS, gig, Serialization,
typeinfo) of which LYNX needs a read-only subset, and its loaders allocate whatever sizes a file declares and signal
errors with exceptions. LYNX has three hand-kept build lists (CMake, `build-local.sh`, `build-windows-zig.sh`). LYNX's
own reader (`src/core/GigFile.cpp`, ~650 lines) reads chunk headers through bounded `readAt` calls (a large library
is never loaded whole), caps every parameter chunk at 1 MB and every sample at 512 MB, and gives up quietly on
anything that does not add up. THIRD_PARTY.md lists libgig as the format reference.

### 2.2 Layout [SPEC]

`RIFF 'DLS '`: `vers` (u16 minor, u16 major, …: major 3 = GigaStudio 3/4), `ptbl` (u32 header size, u32 count, then
u32 offsets — or (u32 file number, u32 offset) pairs when the table is twice as long: GigaStudio 3's extension files
`.gx01…`; for files of 2 GB and more the pair is a 64-bit offset), `LIST lins` → `LIST ins ` (`insh`, `LIST INFO`
`INAM` name, `LIST lrgn` → `LIST rgn ` / `rgn2`), `LIST wvpl` (or `dwpl`) → `LIST wave` (`fmt `, `data`, `wsmp`,
`smpl`, `3gix`, `ewav` = compressed). A pool offset counts from the start of the pool list's data to the wave's
`LIST` header. `xfil`: u32 count, then 144-byte entries (128-byte name + 16-byte id) of the extension files.

Region: `rgnh` (key low / high, velocity low / high, options, key group), `wsmp` (DLS sampler record), `wlnk` (pool
index), `3lnk` (u32 dimension-region count, then 5 (gig 2) or 8 (gig 3) dimension definitions of 8 bytes: type,
bits, bit position, mask, zone count (gig 3), 3 reserved; then at byte 44 / 68 one u32 pool index per dimension
region), `LIST 3prg` → one `LIST 3ewl` per dimension region (`wsmp`: unity note, fine tune in cents, attenuation in
1/655360 dB, first loop start / length; `3ewa`: the parameters). A dimension region's index is the sum of each
dimension's zone number shifted by its bit position (definition order).

`3ewa` fields LYNX reads (byte offsets): 28 EG1 attack, 32 EG1 decay 1, 38 EG1 sustain (‰), 40 EG1 release (times as
i32 codes: seconds = 1.000000008813822^code), 80 EG1 decay 2 (0x7FFFFFFF = infinite sustain), 104 sample start
offset, 108 bit 0 = no pitch tracking, 109 pan (7-bit signed: 0…63 right, 64…127 = −1…−64), 124 velocity upper
limit (gig 2), 132 bit 7 = filter on, 140…147 the dimensions' upper limits (gig 3; index = definition place).

Velocity zones: custom split points when the zone-0 dimension region of that axis has a non-zero limit (gig 3: its
`3ewa` upper limit for the velocity dimension; gig 2: its velocity upper limit) — zone k spans from the previous
zone's limit + 1 to its own; otherwise even splits of `int(128 / zones)`, the last zone up to 127.

### 2.3 Mapping

| gig | LYNX DirectWave |
|---|---|
| region key range, key group | zone key range, exclusive group |
| velocity dimension | the zones' velocity ranges (custom or even splits), inside the region's own range |
| layer dimension | zones that sound together |
| round robin, round robin over the keyboard | an alternation group per region (and layer), mode Cycle |
| random | an alternation group, mode Random |
| sample channel | its first zone only (the region's sample is played as one stereo zone) |
| release trigger, keyswitch ("keyboard"), smart MIDI, aftertouch, MIDI-controller dimensions | the zone a plain note plays (zone 0); the others are counted in the report |
| unity note, fine tune, attenuation, pan, pitch tracking | root, coarse / fine, gain (≤ 0 dB), pan, key tracking 100 / 0 |
| first loop | forward loop |
| sample start offset | sample offset |
| EG1 attack / decay 1 / sustain / release | amplitude ADSR (DirectWave's laws: t = 10·v⁴ + 0.001 s, the level heard squared) |
| 16-bit PCM | a 16-bit WAV (held as integers like DirectWave); 24-bit PCM → 24-bit WAV; 8-bit → unsigned 8-bit WAV |

Reported as not brought over: compressed samples (`ewav`: GigaStudio's lossless compression), missing extension
files, filters (left off), EG1 decay 2, LFOs, pitch and filter envelopes, velocity curves, crossfades, scripts.
More than 99 round-robin groups wrap (regions then share a counter).

**Checked against libgig's own writer** (offline, nothing committed): a GigaStudio 3 file written by libgig 4.4.1 (an
instrument with a region of 2 velocity zones split at 40 × 2 round-robin zones on four mono samples, unity note 48,
fine +7 cents, 3 dB attenuation, pan −32, EG1 attack 0.01 s / sustain 750 ‰ / release 0.5 s, and a second region
on a stereo sample with a 100 + 300 loop and key group 2) imports as 5 zones with exactly those values (velocity
0–40 / 41–127, one Cycle group, gain 0.708, loop 100–400, exclusive group 2, the envelope values in DirectWave's
laws). That file showed one quirk the reader now tolerates: libgig writes a stereo sample's `fmt ` block alignment
as 2, so the frame size is taken from channels × bits as GigaStudio readers do. No real commercial `.gig` was
available on this PC; gig 2 files are covered by the synthetic test only.

## 3. Kontakt

### 3.1 What is legal and possible [SPEC]

- Kontakt's library format is closed. **Protected (licensed) libraries are encrypted; LYNX never decrypts or works
  around that protection** (no keys, no circumvention). Their `.nkx` / `.nkc` containers are not opened at all.
- **NCW** is Kontakt's lossless sample compression, not a protection. The ncw project (github.com/monomadic/ncw,
  MIT OR Apache-2.0) publishes a byte-level description (FORMAT.md) checked against Kontakt; LYNX's decoder
  (`src/core/Ncw.cpp`) is written from it. Another project, monomadic/ni-file, was taken down after a notice from
  Native Instruments (2024) and was not used.
- **Unencrypted `.nki`** zone maps are documented by ConvertWithMoss (LGPL-3.0, compatible): Kontakt 1 (magic
  0x5EE56EB3, zlib XML `NiSS_Zone`), Kontakt 1.5…4.1 (0x1290A87F + a 0xAA-byte header, zlib XML `K2_Zone` with an
  encoded sample path), the 4.2 header (FastLZ binary presets), and the NI container of Kontakt 4.2.2…8 (`"hsin"` at
  byte 12; items with chains of data chunks; type 116 = Encryption Item, 106 = Authorization, 109 = Preset Chunk;
  the preset's zone list 0x34 / zone 0x2C / file-name list 0x4B).

### 3.2 What LYNX does

- NCW: header (signature `01 A8 9E D6 31|30 01 00 00`, channels, bits, rate, frames, block table at 120, data offset,
  data size), one table entry per 512 frames plus a sentinel, per block one sub-block per channel (16-byte header:
  `16 0C 9A 3E`, base value, signed width, flags), 512 values packed LSB first: deltas (width > 0; the first sample is
  the base value, the 512th delta unused) or raw samples (width < 0); flag bit 0 mid / side (channel 0's flag;
  left = mid + side, right = mid − side, wrapping), bit 1 floats (deltas on the bit patterns). Widths 0 and 1 are
  refused (Kontakt has no decoder for them). The frame count is bounded by the file size before any allocation.
  `.ncw` is a sample extension (`core/SampleFiles.h`) and a JUCE format (`engine/NcwFormat.cpp`, registered with
  LYNX's MP3 reader), so the Browser lists, previews and drops it like a WAV, and DirectWave / sampler zones can
  point at it.
- `.nki`: `kontakt::detect` tells the versions apart; for the NI container a bounded walk of the item tree looks for
  an Encryption Item. The import dialog says which kind it is, that protected libraries are not opened, and that
  Kontakt itself loads as a plugin. **Not done this round**: reading the zone maps of unencrypted Kontakt 1 / 2 XML
  and 4.2+ container instruments (needs the K2 encoded-path decoder, FastLZ and the preset object tree, and real
  unprotected test files; ConvertWithMoss describes all three). `.nkm` multis are not handled.

**Checked against the ncw project's reference files** (offline, not committed): all seven fixtures with a reference
WAV (16-bit mono / stereo, 24-bit mono, 32-bit float mono / stereo, two single-/multi-block 16-bit stereo files)
decode sample for sample identical to their WAVs (0 differing samples), including raw blocks at −16 / −32 and
delta widths 2…26.

## 4. Browser and drop

`.dwp`, `.dwb`, `.gig` are listed (preset icon; "Samples and SoundFonts" and "Presets" filters), `.ncw` with the audio
files. Double click / "Open in a new channel": a new DirectWave channel; Enter / "Send to the selected channel": into
the selected DirectWave channel (its mixer track, levels and notes stay); a drop on the Channel Rack: onto a DirectWave
channel replaces its program, elsewhere a new channel. A `.gig` with several instruments opens a menu of them. The
import runs off the message thread; a dialog lists what was not brought over (missing samples, skipped dimensions,
compressed samples, …) or why nothing was imported. `.nki` is not listed (nothing to import yet) but a dropped one
gets the explanation.

## 6. For the rollup with round 190hz

- The hook is `dw::importChannel` (DirectWave.h, unchanged); no editor file is touched. After the merge the
  editor opens these channels like any DirectWave channel (a one-program state; 190hz's document functions accept it).
- 190hz's `readProgramFile` (the editor's "Open program") reads `.dwp` through `readZone`, which skips the 36-byte
  sample format records of version-36 programs (§1.2): it can pass the file through `msimport::stateOfFile` first,
  or `readZone` can accept 36 bytes (bits = 32).
- Optional: build imported programs as FL's full 128-program bank (190hz's `freshDoc` + `loadProgram`) so a later
  "Bank save as" writes what FL would.
- Text lists of formats (README, site, app, FAQ, Store): add `.dwp`, `.dwb`, `.gig` (instruments) and `.ncw`
  (samples).
